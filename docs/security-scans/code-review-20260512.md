# Code Review & Security Scan — AuthPlatform

**Date:** 2026-05-12  
**Reviewer:** Antigravity (AI-Assisted)  
**Scope:** Full codebase (`src/`, `tests/`, configuration, Docker)  
**Framework:** .NET 9, Clean Architecture (CQRS + MediatR)

---

## Executive Summary

The AuthPlatform codebase follows Clean Architecture with well-separated layers and solid foundational security practices (RS256 JWT, BCrypt, refresh token rotation, rate limiting). The code is readable and idiomatic C#.

However, this review surfaces **5 Critical**, **8 Important**, and **9 Minor** findings across security, correctness, architecture, and performance that should be addressed before production deployment.

| Severity | Count | Summary |
|----------|-------|---------|
| 🔴 **Critical** | 5 | Must fix before production — data loss, security vulnerability, or broken functionality |
| 🟠 **Important** | 8 | Should fix — correctness, reliability, or defense-in-depth issues |
| 🟡 **Minor / Nit** | 9 | Improvement opportunities — performance, maintainability, conventions |

## 1. Security Findings

### 🔴 SEC-01: Hardcoded Database Credentials in appsettings.json (Critical)

**Files:** `appsettings.json:12`, `appsettings.Development.json:9`

Both files contain `User=root;Password=root;` in `ConnectionStrings`. Even though `.gitignore` covers `appsettings.*.local.json`, the base `appsettings.json` **is tracked in version control** and contains cleartext credentials.

```json
"DefaultConnection": "Server=localhost;Port=3306;Database=auth_platform;User=root;Password=root;"
```

**Risk:** Credential exposure in VCS history; root-level DB access in production defaults.

**Recommendation:**
- Remove the password from tracked config files — use a placeholder like `__REPLACE_ME__`
- Use User Secrets (`dotnet user-secrets`) for local development
- Use environment variables or Azure Key Vault / Docker secrets for production

---

### 🔴 SEC-02: Hardcoded Seed Passwords in Source Code (Critical)

**File:** `ApplicationDbContextSeed.cs:196-210`

Development seed data contains hardcoded passwords (`Admin@123`, `Viewer@123`) and a static API key (`"default-api-key"`). If `ASPNETCORE_ENVIRONMENT` is accidentally left as `Development` in production, these weak credentials are seeded.

```csharp
BCrypt.Net.BCrypt.HashPassword("Admin@123", workFactor: 12)
```

**Risk:** Attackers with knowledge of the source code can authenticate as admin in a misconfigured deployment.

**Recommendation:**
- Gate development seed behind `#if DEBUG` or a compile-time constant rather than environment name
- Log a loud WARNING when development seed runs
- Consider requiring force-change-password on first login for seeded accounts

---

### 🔴 SEC-03: Missing Security Response Headers (Critical)

**Files:** `Program.cs`, `ApplicationBuilderExtensions.cs`

No security headers are configured. The application is missing:
- `Strict-Transport-Security` (HSTS)
- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: DENY`
- `Content-Security-Policy`
- `Referrer-Policy`
- `Permissions-Policy`

**Risk:** Susceptible to clickjacking, MIME-type sniffing, and protocol downgrade attacks.

**Recommendation:**
```csharp
// In Program.cs — after UseApiMiddleware, before UseAuthentication
app.UseHsts();
app.Use(async (context, next) =>
{
    context.Response.Headers["X-Content-Type-Options"] = "nosniff";
    context.Response.Headers["X-Frame-Options"] = "DENY";
    context.Response.Headers["Referrer-Policy"] = "strict-origin-when-cross-origin";
    context.Response.Headers["Permissions-Policy"] = "camera=(), microphone=(), geolocation=()";
    await next();
});
```
Or use the [NWebsec](https://github.com/nwebsec/NWebsec) middleware package.

---

### 🔴 SEC-04: API Key Generated from Guids — Not Cryptographically Strong (Critical)

**File:** `ApplicationsController.cs:95`

API keys are generated by concatenating two `Guid.NewGuid().ToString("N")`, which are **not cryptographically random** (they use UUID v4, which provides ~122 bits of randomness but in a predictable format).

```csharp
var apiKey = Guid.NewGuid().ToString("N") + Guid.NewGuid().ToString("N");
```

**Risk:** Weakened API key entropy; format is recognizable, aiding brute-force targeting.

**Recommendation:**
```csharp
var bytes = RandomNumberGenerator.GetBytes(32);
var apiKey = Convert.ToBase64String(bytes);
```

---

### 🔴 SEC-05: Tenant ConnectionString Exposed via Update API (Critical)

**File:** `TenantsController.cs:116-126`

The `UpdateTenant` endpoint accepts a `ConnectionString` parameter in the request body. An attacker with `tenants.manage` permission could inject a malicious connection string pointing to an attacker-controlled database, or perform SQL connection string injection.

```csharp
public record UpdateTenantRequest(string Name, string? ConnectionString);
```

**Risk:** SSRF via connection string injection; potential data exfiltration.

**Recommendation:**
- Do NOT accept connection strings through the API
- Store and manage connection strings through infrastructure configuration only
- If runtime connection strings are needed, validate against an allowlist of hosts

---

### 🟠 SEC-06: Refresh Token Endpoint Missing Rate Limiting (Important)

**File:** `AuthController.cs:46-59`

The `/api/auth/refresh` endpoint is `[AllowAnonymous]` but has **no rate limiting** applied (unlike the login endpoint which has `[EnableRateLimiting("Login")]`).

**Risk:** An attacker can rapidly enumerate or brute-force refresh tokens without throttling.

**Recommendation:** Add `[EnableRateLimiting("Login")]` or a dedicated policy to the refresh endpoint.

---

### 🟠 SEC-07: Audience Validation Disabled in JWT (Important)

**File:** `ServiceCollectionExtensions.cs:82`

```csharp
ValidateAudience = false,
```

The JWT audience is set during token generation (`audience: applicationCode`) but never validated on incoming requests. A token issued for app "X" would be accepted by app "Y" if they share the same signing key.

**Risk:** Token misuse across applications sharing the same AuthPlatform.

**Recommendation:** Set `ValidateAudience = true` and configure `ValidAudiences` per deployment, or validate the `app` claim in the authorization handler.

---

### 🟠 SEC-08: RSA Key Leaked via IServiceProvider — Key Material in Memory (Important)

**Files:** `ServiceCollectionExtensions.cs:52-67`, `JwtService.cs:115-134`

The RSA object is created but its private parameters are exported and the RSA instance is never disposed. In the `JwtService`, a new RSA key is created per token generation call (`RSA.Create()`) and never disposed.

**Risk:** Memory leak of RSA key material; key data lingering in managed heap.

**Recommendation:** Cache the RSA key as a singleton at startup rather than recreating per call. Ensure proper disposal via `IDisposable`.

---

### 🟠 SEC-09: No JWT Blacklist/Revocation Check (Important)

**Architecture notes mention:** "JWT jti added to blacklist (Redis cache until JWT expiry)"  
**Actual implementation:** No blacklist check exists anywhere.

The `RevokeTokenCommand` only revokes the refresh token. Once a JWT is issued, it remains valid until expiry. If a user logs out, their access token continues to work.

**Risk:** Logged-out users retain access for up to `AccessTokenExpirationMinutes` (15-60 mins).

**Recommendation:** Implement a JTI-based blacklist using the `CacheService`. Check the blacklist in a custom JWT bearer event (`OnTokenValidated`).

## 2. Correctness Findings

### 🟠 COR-01: User.VerifyPassword Does Not Use BCrypt (Important)

**File:** `User.cs:66-69`

```csharp
public bool VerifyPassword(string passwordHash)
{
    return PasswordHash == passwordHash;
}
```

This method compares raw strings rather than using BCrypt verification. It's **not currently called** from production code (the `LoginCommandHandler` correctly uses `IPasswordHasher.Verify`), but its existence is misleading and dangerous — any future caller would bypass BCrypt's timing-safe comparison.

**Risk:** If invoked, it performs plaintext comparison, bypassing hash verification and enabling timing attacks.

**Recommendation:** Either delete this method (it's dead code) or fix it to delegate to `IPasswordHasher`. Domain entities shouldn't contain password verification logic.

---

### 🟠 COR-02: UpdateUser Endpoint Missing Tenant Isolation (Important)

**File:** `UsersController.cs:159-169`

The `UpdateUser` and `DeleteUser` endpoints use `_context.Users.FindAsync(id)` without tenant-scoped filtering, unlike `GetUsers` and `GetUser` which apply tenant isolation.

```csharp
public async Task<IActionResult> UpdateUser(Guid id, ...)
{
    var user = await _context.Users.FindAsync(id);  // No tenant check!
```

**Risk:** A user in Tenant A could modify or delete a user in Tenant B if they know the target user's GUID.

**Recommendation:** Apply the same tenant isolation query as `GetUser` to all mutating operations.

---

### 🟠 COR-03: CreateUser Not Scoped to Tenant (Important)

**File:** `UsersController.cs:121-150`

When creating a new user, no `TenantId` is assigned. The created user has `TenantId = null`, making them a "global" user even in a multi-tenant environment.

**Recommendation:** Assign `TenantId` from `_tenantService.CurrentTenantId` when creating users, or require it in the request.

---

### 🟡 COR-04: Duplicate Email/Username Check Not Tenant-Scoped (Minor)

**File:** `UsersController.cs:123-124`

```csharp
var existingUser = await _context.Users
    .FirstOrDefaultAsync(u => u.Email == request.Email || u.Username == request.Username);
```

This searches globally, preventing the same email from being used across different tenants. This may be intentional but should be documented.

---

### 🟡 COR-05: Login Lockout Checked After Password Verification (Minor)

**File:** `LoginCommand.cs:44-52`

The code verifies the password first, then checks if the account can login. If the account is locked, the failed password attempt is still recorded and the lockout timer is potentially extended.

```csharp
if (!_passwordHasher.Verify(request.Password, user.PasswordHash))
{
    user.RecordFailedLoginAttempt(5, 15);  // Extends lockout even if already locked
    ...
}

if (!user.CanLogin())
    return AuthenticationResult.Failed("Account is locked or inactive.");
```

**Recommendation:** Check `user.CanLogin()` **before** verifying the password to avoid unnecessary BCrypt computation and lockout extension on already-locked accounts.

## 3. Architecture Findings

### 🟡 ARCH-01: Controllers Directly Access DbContext (Bypassing CQRS) (Minor)

**Files:** `UsersController.cs`, `RolesController.cs`, `PermissionsController.cs`, `ApplicationsController.cs`, `TenantsController.cs`

Only `AuthController` uses MediatR/CQRS. All other controllers inject `IApplicationDbContext` directly, bypassing:
- `ValidationBehavior` (no FluentValidation for create/update requests)
- `LoggingBehavior` (no structured command logging)
- `PerformanceBehavior` (no slow-query detection)

The `Application/Features/` directory only contains `Auth/` commands — the planned `Users/`, `Roles/`, `Permissions/`, `Applications/` features from `ARCHITECTURE.md` are not implemented.

**Impact:** Inconsistent validation, no audit trail through MediatR pipeline, architecture diverges from documented design.

**Recommendation:** Migrate CRUD operations to MediatR commands/queries with validators. This is a significant effort but aligns with the intended architecture.

---

### 🟡 ARCH-02: DTOs Defined Inline in Controller Files (Minor)

**Files:** All controller files

Request and response DTOs (`LoginRequest`, `CreateUserRequest`, `RoleDto`, `PermissionDto`, etc.) are defined at the bottom of controller files. This violates separation of concerns and makes DTOs hard to share or discover.

**Recommendation:** Move DTOs to `Auth.Application/Common/Models/` or introduce a `Contracts` namespace.

---

### 🟡 ARCH-03: Persistence Layer Has BCrypt Dependency (Minor)

**File:** `Auth.Persistence.csproj:22`

`BCrypt.Net-Next` is referenced in both `Auth.Infrastructure` (where `PasswordHasherService` lives) and `Auth.Persistence` (for seed data). The Persistence layer should not have password hashing concerns.

**Recommendation:** Accept a pre-hashed password in the seed method, or inject `IPasswordHasher` into the seed process rather than adding a direct BCrypt dependency.

---

### 🟡 ARCH-04: Missing AuthorizationBehavior Registration (Minor)

**File:** `DependencyInjection.cs` (Application)

`ARCHITECTURE.md` lists an `AuthorizationBehavior` in the MediatR pipeline, but it's neither implemented nor registered. Only `ValidationBehavior`, `LoggingBehavior`, and `PerformanceBehavior` are wired.

---

## 4. Performance Findings

### 🟡 PERF-01: No AsNoTracking() on Read-Only Queries (Minor)

**Files:** All controller GET actions

Every read query uses full EF Core change tracking. For paginated list endpoints that return DTOs (never saved back), this wastes memory and CPU.

```csharp
var query = _context.Users
    .Include(u => u.UserRoles)
        .ThenInclude(ur => ur.Role)
    .AsQueryable();  // Missing .AsNoTracking()
```

**Impact:** ~15-30% overhead per read query; compounds under load.

**Recommendation:** Add `.AsNoTracking()` to all read-only queries.

---

### 🟡 PERF-02: Deep Include Chain in RefreshTokenService (Minor)

**File:** `RefreshTokenService.cs:55-64`

```csharp
.Include(rt => rt.User)
    .ThenInclude(u => u.UserRoles)
        .ThenInclude(ur => ur.Role)
            .ThenInclude(r => r.RolePermissions)
                .ThenInclude(rp => rp.Permission)
.Include(rt => rt.User)
    .ThenInclude(u => u.UserPermissions)
        .ThenInclude(up => up.Permission)
```

This 5-level deep include chain loads a large object graph on every token refresh. Consider using a projection query or caching the permission set.

---

### 🟡 PERF-03: Pagination pageSize Not Bounded (Minor)

**Files:** All paginated GET endpoints

```csharp
public async Task<IActionResult> GetUsers([FromQuery] int page = 1, [FromQuery] int pageSize = 10)
```

There's no upper limit on `pageSize`. A client could request `pageSize=999999`, bypassing pagination.

**Recommendation:** Clamp `pageSize` to a maximum (e.g., 100):
```csharp
pageSize = Math.Clamp(pageSize, 1, 100);
```

## 6. Configuration & DevOps Findings

### 🟠 CFG-01: CORS "AllowAll" Policy Name is Misleading in Production (Important)

**File:** `ServiceCollectionExtensions.cs:19-38`

Both development (allow any origin) and production (restricted origins) CORS policies share the same name `"AllowAll"`. The production policy is actually restrictive, but the name is confusing and error-prone.

**Recommendation:** Rename to `"DefaultCors"` or `"ApiCors"`.

---

### 🟡 CFG-02: Docker Compose Uses Default Root Password (Minor)

**File:** `docker-compose.yml:32`

```yaml
MYSQL_ROOT_PASSWORD: ${MYSQL_ROOT_PASSWORD:-root}
```

The default fallback is `root`. While it's behind an env var, developers may deploy with defaults.

---

### 🟡 CFG-03: Dockerfile Runs as Root (Minor)

**File:** `Dockerfile`

No `USER` directive is specified. The container runs as root by default.

**Recommendation:** Add a non-root user:
```dockerfile
RUN adduser --disabled-password --gecos '' appuser
USER appuser
```

## Verdict

### ❌ **Request Changes** — Issues must be addressed before production deployment

The 5 Critical security findings (hardcoded credentials, missing security headers, weak API key generation, connection string injection) represent real attack surfaces that must be resolved. The codebase foundation is solid and well-structured, but needs the security hardening pass outlined above before it can safely serve as an enterprise auth platform.
